2026 年 7 月 28 日，MCP（Model Context Protocol）发布了自 2024 年 11 月诞生以来规模最大的一次规范更新。官方公告用了"最大规模"这个词，没有任何保留。

表面上的变化很清楚：会话机制与初始化握手流程被移除，协议核心转为无状态架构。但这个描述掩盖了真正重要的问题：**谁将在这个决定中被重新分配权力**。

## 发生了什么：协议的自我简化

先说技术事实。

MCP 原来的设计依赖会话机制：客户端与 MCP 服务器建立长连接，服务器维护会话状态来完成请求处理。这次更新把这个机制从协议层删掉了，改为**每次请求携带完整处理所需信息**，服务器不再需要记住"上一次对话说了什么"。

配套的变化还包括：

- 引入**版本化扩展框架**，正式纳入 MCP Apps 与 Tasks 扩展
- 强化 OAuth 2.0 与 OIDC 生产部署适配，可直连微软 Entra、Okta 等企业身份系统
- 引入完整 JSON Schema、能力发现（Capability Discovery）和标准化链路追踪

这些改进对生产环境确实有价值。但把它们放在一起看，一个更大的逻辑浮现出来。

## 真正的问题：状态让渡给谁

会话机制的消失意味着状态管理必须去往别处。

在原来的架构里，MCP 服务器持有会话状态——它知道你在哪一步、积累了哪些上下文。对于需要长期运行的任务，这是必要的。但对于需要水平扩展的生产系统，会话状态是致命的：状态在内存里，服务器不能重启，不能水平扩展，不能轻易做负载均衡。

传统解法是将会话状态外置到 Redis 或其他存储。但这是变通，不是协议原生支持。

这次 MCP 的选择是：**把状态管理完全归还给客户端和已有基础设施**。协议本身不再承载状态，服务器变成纯函数式的请求处理器。

这意味着什么？

**云厂商赢了。** 当协议层不再承载状态，状态管理的责任滑向了两个地方：调用方（LLM 应用侧）和平台侧（云厂商的 AI 网关/Agent 运行时）。而这两者都不是开源社区能控制的。Anthropic 发布了协议，但真正决定生产系统怎么跑的人，是云厂商。

这不是阴谋，这是自然演化。任何协议在企业级部署面前，都会被"谁持有状态"这个问题重新塑造。MCP 团队选择了把烫手山芋递出去。

## 扩展框架：一个更聪明的绑定方式

无状态化拆掉了旧的东西，扩展框架则在建立新的连接。

MCP Apps 和 Tasks 这两个扩展，前者支持交互式界面，后者支持长时间运行任务。两者都不是协议核心的一部分，却恰好填补了无状态化留下的能力缺口。

更值得注意的细节是**扩展的版本化**。这意味着第三方可以在不修改核心协议的情况下发布自己的扩展，协议本身保持稳定。对外宣传的是"不伤及核心的扩展性"，但实际上这是一种**受控的厂商锁定**——只要核心稳定，谁的扩展做得好，谁就占据了生态位。

## 授权加固：企业市场的入场券

OAuth 2.0 和 OIDC 的原生支持，是这次更新里最被低估的变化。

在 2024 年的初始版本里，企业身份集成（Entra/Okta）需要变通方案。这对于互联网开发者是无所谓的，但对于金融、医疗、政府等强合规行业，不可接受。

这次更新直接在内层解决，代价是协议复杂度上升。但对于企业市场，这是一张入场券。没有这个，企业安全团队连 POC 都不会批准。

## 一周内的另一个信号

同周，A2A 协议（Agent-to-Agent）宣布生产部署突破 150 家组织。中国发布了 GB/Z 185-2026《智能体互联互通》标准，29 国在上海签署 WAICO 创始文件。

如果把这些事件放在一起看，叙事就更清晰了：**Agent 互联互通的标准化竞争正在加速**。MCP 解决的是"模型与工具的连接"，A2A 解决的是"Agent 与 Agent 的连接"，两条线在同一周内都有重大进展。这不是巧合，是竞争压力下的同步冲刺。
